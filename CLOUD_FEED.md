# Independent cloud VLESS subscription

The existing `verified/live-vless.txt` is written by **GWZHUB Publisher**, outside this
GitHub Actions workflow. Its published `Количество: 0` is not repaired by this service.

An independent feed will be published on the `main` branch:

`https://raw.githubusercontent.com/gwz-tools/config-hub/main/cloud-vless.txt`

It will exist **only after a successful cloud workflow run**. Do not configure routers
with that URL before verifying that it contains at least three `vless://` entries.

## How it works

- Reuses `data/gwzhub_candidates.txt` generated by the existing main collector.
- Tests public VLESS endpoints by starting a temporary sing-box HTTP proxy per candidate.
- All HTTPS checks are sent **through that VLESS tunnel**: an initial Google 204 endpoint,
  then Gemini, Instagram, Facebook (Meta), and YouTube.
- A candidate passes only if the control URL responds successfully and all four service URLs return HTTP 2xx/3xx. HTTP 401/403/429 is not counted as an
  accessible service. A success from a GitHub runner **does not guarantee access in
  Russia or on a particular ISP**.
- Only publishes if at least three nodes pass. Otherwise retains an existing non-empty
  `cloud-vless.txt`; if none exists the workflow fails without publishing a zero list.
- No private VLESS subscription URLs or authentication tokens should be committed here.
  Configure any private source later with encrypted GitHub Actions secrets.

## Publication and failover

Scheduled at minute 17 every six hours UTC (after the existing 6-hour collector).
Metadata: `data/cloud-status.json`, with counts only. Test all four services, but
do not overstate the result as full website functionality or video playback.

The independent feed is a GitHub Raw URL and may itself use non-domestic infrastructure.
This **reduces upstream requests** from the router but does not bypass ISP charging for
foreign-IP VPN traffic.

A Dropbox / Yandex Disk mirror must be configured separately with credentials and
write permissions; the public mirror must never disclose an API key.

## The original GWZHUB publisher

An additional guard must be installed **on GWZHUB itself** before it uploads to the
`verified` branch. The on-hub publisher is not part of this repository. Reject empty
or malformed output before the API upload, preserve a last-good VLESS snapshot, and
do not advertise the feed as fresh when the last good version is stale.


## Optional Dropbox replication from GitHub Actions

The workflow includes a step that uploads the same validated file to
`/GWZHUB/cloud-vless.txt` using `mirror_dropbox.py`. This step is **disabled**
until all three repository Actions secrets are supplied:

- `GWZ_DROPBOX_APP_KEY`
- `GWZ_DROPBOX_APP_SECRET`
- `GWZ_DROPBOX_REFRESH_TOKEN`

Create a Dropbox API app with scoped `files.content.write` permission and an
offline/refresh token. Add secrets under repository **Settings → Secrets and
variables → Actions**. Never paste tokens into repository files or chat.

The mirror is best-effort (`continue-on-error`): a Dropbox API outage cannot
roll back the valid GitHub feed. A Dropbox download link must be created and
checked separately; uploading alone does not create a public subscription URL.

## Ranked cloud tunnel history (Step 2)

The 6-hour `cloud-verified.yml` run now rotates candidates across the complete
geographically balanced discovery list. Up to one third of each batch retests
previously successful nodes; the remainder explores candidates not reached by
previous runs. This prevents permanent first-48 selection bias.

`cloud_health.py` keeps a bounded `data/cloud-health.json` ledger of actual
VLESS **tunnel** tests, indexed by SHA-256 connection fingerprint (no VLESS URI,
UUID, hostname or secret in the ledger). Each tested node stores up to 32
observations for seven days. Unprobed nodes are not failures, and an all-zero
cloud run does not count against nodes (the rotation cursor still advances).

Published candidates must pass HTTPS via their own tunnel **during this run**.
They are ranked 45% 24h success rate, 35% seven-day success rate (both
smoothed), 15% latency, 5% freshness. This is **cloud vantage availability**:
it is not a speed test, Russian ISP check, guarantee of future availability,
or a replacement for local Podkop URLTest checks. After an insufficient passing
sample, the last-good subscription stays in place.

The existing public `cloud-vless.txt` remains the consumption format. There is
no change to any router. The health ledger is bounded to 500 nodes so GitHub
does not become a new history warehouse.

## Step 3: entry/exit subnet and ASN diversity

The cloud runner now requires metadata for both the **actual resolved entry IP**
and the **outgoing IP as seen THROUGH the tested VLESS tunnel**, not a country
label from the URI. Both are looked up through the free HTTPS `ipwho.is` API
after a successful HTTPS functional check. Unknown, non-global or Russian
(`RU`) endpoints are rejected from *newly published* feeds. The geolocation
service is an external dependency and its database is only an estimate.

Only individually successful tunnels are eligible. The selection first
prioritizes different entry ASN and exit ASN, then allows a maximum of two
servers per ASN, while enforcing one entry IPv4 /24 or IPv6 /48 and a maximum
of three per exit country. These limits intentionally reduce duplicate failure
domains at the cost of a smaller subscription.

At least **three** independently eligible nodes are required before replacing
`cloud-vless.txt`. If that threshold is not met, the existing feed is
retained with metadata indicating stale reuse. A previous list published
before this policy is **not retroactively guaranteed to be diverse**.

New checks use 64 rotating candidates every six hours. Metadata reports
counts of distinct entry subnets, entry ASNs, exit ASNs and exit countries;
raw credentials, client UUIDs and exact exit IPs are not added to metadata.
An ASN is a useful network-operator signal but cannot guarantee independent
hardware or routing. Checks from a GitHub cloud runner do not guarantee
reachability from Russian ISPs; local OpenWrt/Podkop verification remains
essential.
